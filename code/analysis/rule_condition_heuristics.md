# Rule conditions the current code decides with heuristics

Source: `code/data/states.py` (category + reading), `code/fallback.py` (linking, retention, discovery). "Model reader" = what the new facts-only reader would supply; the deterministic pipeline still makes the decision.

| Rule (condition) | How the code decides today | Gap / what the reader would replace |
|---|---|---|
| rule_05 SUPPORT_MESSAGE: conversation contains shared customer, agent or order context -> REDACT | Never evaluated. Every support message is treated as REDACT. Reading: `IDENTIFIABLE` if a PII-scan hit, `matched_value`, a non-null requester field or an email in `message_text`; `REDACTED` if `[redacted]` text or null requester fields. | Condition false (no shared context) is never considered; the rules give no action for that branch. Reader: does the conversation carry shared customer/agent/order context (from `message_text`/`message_excerpt`, tickets, PDFs)? |
| rule_06 SUPPORT_ATTACHMENT: belongs only to the deletion subject -> DELETE | Category by heuristics: source `ticket_attachments`, `storage_class`, PDF file, or an attachment event. Always DELETE; sole ownership is never checked. | Reader: does the attachment (PDF text, file name, ticket) involve only the subject, or other customers/shared orders? |
| rule_07 ANALYTICS_PROFILE: still attributable to a user -> ANONYMIZE | "Attributable" = any of email, phone, email_hash, user_id, customer_reference non-null, or `direct_identifiers>0` / `matched_value`; otherwise anonymized. | Free-text fields (recent activity, cohort text) and screenshots are not inspected for indirect identifiers. |
| rule_08 PRODUCT_TELEMETRY: still attributable -> ANONYMIZE | No telemetry category exists in the code (no resource prefix known). | Unhandled until such evidence is seen. |
| rule_11 EMAIL_DELIVERY_LOG: contains a user email -> REDACT | Category by prefix only; reading is `FOUND`, so it can never become a violation. No `email_delivery_` resource appears in any text evidence or sample answer. | Unhandled; may only exist in screenshots/PDFs. |
| rule_12 SECURITY_AUDIT_LOG: within retention period -> RETAIN | Any audit record that exists is `RETAINED`; `retention_until` is never compared with `audit_at`. | Reader/code: is `retention_until` after `audit_at` (ledger, SQL, PDF extract)? Expired records would not be retained. |
| rule_13 LEGAL_HOLD_RECORD: a legal hold is active -> RETAIN | Any `legal_hold_` record that exists is `RETAINED`. The retention register PDF is only used for identity links. | Reader: is a hold active (register PDF, `retained_until`)? |
| rule_14 BACKUP_ARCHIVE: restore access can be blocked -> RETAIN | Restorable (`restore_allowed`, `eligible`/`deletion_block`, ledger `ACTIVE`) = violation; blocked = clean. "Can be blocked" is assumed true. | Reader: can restore access be blocked, or must the archive itself be deleted? |
| rule_15 ACCOUNT_TOMBSTONE: account deleted, only stable user_id needed -> REDACT | Name, email, phone or hash present = `IDENTIFIABLE` (exposed); none = redacted. The "account is deleted" and "only user_id retained" parts are not checked. | Reader: does the tombstone keep only `user_id`/`subject_reference` and do other fields belong to the subject? |
| Unconditioned rules (profile, secondary identifier, search, cache, export, marketing: DELETE) | Category from resource prefix plus record_type/collection/event: `contact_lookup`/`email_opt_in` -> marketing (kept under analytics_platform), `contact_query`/`deletion_marker`/legacy contact index -> secondary identifier. Reading from `rows`, `http_status`, `result`, `profile`, hit/miss. | Unparsed or unfamiliar log dialects, PDF/PNG-only records. |
| Request intent | Replaced by the intent reader (this change). | -- |
